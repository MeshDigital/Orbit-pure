# Cue Forge — Architecture Reference

## Purpose

Cue Forge is ORBIT's dedicated DJ cue editor. It gives a full-track waveform view with interactive cue placement, loop editing, and structural phrase visualization. It is separate from the Workstation — the Workstation plays and mixes, Cue Forge prepares and edits the underlying cue data that gets exported to Rekordbox or loaded onto CDJs.

## Data Flow

### Track Load

```
Right-click track → TrackOperationsViewModel.ExecuteOpenInCueForge
  │
  ├─ SetPlaylistTracks(CurrentProjectTracks)    ← populates left browser sidebar
  ├─ CueForgeViewModel.LoadTrackAsync(hash, title, artist)
  │     ├─ ICuePointService.GetByTrackIdAsync   ← loads committed cues from DB
  │     ├─ ILibraryService.GetAudioFeaturesByHashAsync
  │     │     ├─ WaveformBlob [Low|Mid|High bytes] → WaveformLow/Mid/High
  │     │     ├─ EnergyCurveJson                → EnergyCurveData float[]
  │     │     ├─ VocalDensityCurveJson          → VocalDensityCurveData float[]
  │     │     ├─ BeatGridJson + OnsetDensityEngine → OnsetDensityCurveData float[]
  │     │     ├─ PhraseSegmentsJson             → PhraseSegments collection
  │     │     └─ CamelotKey                     → CurrentCamelotKey display
  │     └─ AppConfig.CueForgeLastTrackHash saved (session persistence)
  │
  └─ NavigateToPageEvent("CueForge")            ← page becomes visible
```

### Auto-Generate Cues

```
⚡ Auto-Generate button
  │
  └─ CueForgeViewModel.AutoGenerateCuesAsync
        ├─ ILibraryService.GetAudioFeaturesByHashAsync
        ├─ ILibraryService.GetPhrasesByHashAsync → PhraseSourceResolver.Resolve
        │     TrackPhrases rows when present, else PhraseSegmentsJson only when its
        │     PhraseSegmentsSource is trusted (RekordboxPSSI / Heuristic)
        ├─ BuildAnalysisResultFromFeatures(features, phrases) → AnalysisPipelineResult
        │     (fast path: reconstructs signal bundle from DB cache, no audio re-decode;
        │      also carries HintedDropTimestamp from TimeTillDropSeconds / DropTimeSeconds)
        └─ Engine.Cueing.CueGenerationService.GenerateCues(...)
              │
              ├─ Path 1 (phrase): PhraseSegments.Count >= 2
              │     Rekordbox PSSI / Heuristic phrase segments → 8 structurally-driven cues
              │
              ├─ Path 2 (DSP): SubBassReturnTimestamps or NoveltyDropSignatures
              │     Sub-bass silence = breakdown, return = drop
              │     NoveltyDropSignature.BuildStartSeconds = build
              │     EnergyCurve tail falloff = outro
              │
              └─ Path 3 (Heuristic): transient clustering + IntentClassifier
                    Fallback when no sub-bass signals are available
```

**Drop choice is a vote, not a single signal** (`GenerateCuesDsp` → `MergeDropCandidates`):
phrase drops, the stored drop hint, sub-bass returns, spectral-flux novelty, energy jumps and
the genre family's own return signal all vote. Votes landing within two bars of each other merge,
and every agreeing *other* source adds a corroboration bonus, so three weak-but-agreeing
detections beat one loud false positive. Before this, every sub-bass return scored the same when
the flux curve was missing from the cache (it always is), so the earliest return in the window
won — placing `[DROP 1]` 21 s early on TR Tactics — Against The Grain.

**Phrase drops are not bar-snapped.** Phrase starts are already musical boundaries, and the
detected downbeat's bar phase is not reliable enough to move them: on that same track the
downbeat sat three beats late, so an 8-bar snap moved a correct 66.21 s drop to 67.24 s. Drops
are cleaned up at beat resolution instead; DSP drops are only phrase-snapped while that stays
within ¾ bar. The build-in cues stay exact bar arithmetic back from the chosen drop.

**Clear cues.** The AUTO-GENERATE panel (and the Preparation flyout) has a one-click
`Clear cues & reset view`: the whole working set is replaced with an empty list as a single undo
step, and zoom/scroll return to the whole-track view (the playhead returns to 0 when stopped).

### Cue Snapping

Every cue placement (auto or manual) goes through `SnapToBar`:
```
raw_time → SnapToBar(t, bpm, downbeatAnchor)
         = T₀ + ⌊(t - T₀) / (bar_duration) + 0.5⌋ × bar_duration
```
Where `bar_duration = 60/BPM × 4`. Manual edits snap through `CueEditorSession.SnapTime`
(`CueForgeGrid.Snap`: precise BPM, anchored at the downbeat) with the session's `SnapToGrid` +
`SnapResolution` (Beat / Bar / 4 bars / 8 bars). Drops always land on a bar. Cue Forge's waveform
snaps live while dragging using the same session values; the Flow Builder deck snaps on release.

### Save Path

```
Save (Ctrl+S in Cue Forge, "Save cues" on a deck, auto-save on track / pair switch)
  │
  └─ CueEditorSession.SaveAsync
        ├─ ICuePointService.DeleteAllByTrackIdAsync(hash)
        ├─ ICuePointService.CreateManyAsync(Cues → CuePointEntity[])   (touched cues are IsAutoGenerated=false)
        ├─ failure → working set + dirty flag kept, error on the status line, returns false
        └─ success → Saved event, then CueSessionRegistry tells the other sessions on this track
```

There is one save path for every cue editor; the Rekordbox export reads the same rows.

### Export to Rekordbox

```
Playlist export → RekordboxXmlExporter
  └─ per track: CuePointEntity list
        ├─ Type = Drop/Intro/Outro → POSITION_MARK Type="0" (Hot Cue), Num=0..7
        ├─ Type = Loop              → POSITION_MARK Type="4" (Hot Loop), Num=0..7
        └─ Others                   → Memory Cue (no Num/hot pad)
```

## Waveform Control Rendering Pipeline

`CueForgeWaveformControl` renders 10 layers in order (back → front):

1. **Background** — solid `#0A0E27`
2. **Phrase map strip** — bottom 12px colored bands per `PhraseSegment` label (Intro=blue, Drop=red, Breakdown=purple, etc.)
3. **Beat grid** — bar lines (bright) + beat subdivision lines (dim), spaced by BPM
4. **Onset density fill** — translucent yellow/orange fill from `OnsetDensityCurveData`, shows rhythmic activity density
5. **RGB waveform** — `WaveformLow=Red`, `WaveformMid=Green`, `WaveformHigh=Blue` (Rekordbox convention), drawn as vertical lines per sample column
6. **Energy overlay** — bright green line from `EnergyCurveData` (RMS envelope)
7. **Vocal overlay** — red tint strips where `VocalDensityCurveData > threshold`
8. **Loop blocks** — translucent shaded region with draggable `|` edge handles at `LoopInSeconds`/`LoopOutSeconds`
9. **Cue markers** — vertical colored lines + triangle flags per `OrbitCue`, color-coded by `CueRole`
10. **Playhead** — bright cyan vertical line at `CurrentPlayPosition`

**Interaction:**
- Click a cue marker (press + release within 4 px, `MarkerGesture`) → `CueClickedCommand` → `Session.PrelistenCueCommand` (select + play from the exact cue; again = stop)
- Drag a cue marker (past 4 px) → updates `OrbitCue.Timestamp` live, snapped by `ApplySnapping`; the cue never moves before the threshold
- Drag loop edge handles → updates `LoopInSeconds`/`LoopOutSeconds`
- `SnapToGrid` toggle + `QuantizeBeatString` combo drive `ApplySnapping` resolution

## Section markers (Intro end / Outro)

Next to the Intro cue (track start) and `[OUT]` (last usable mix-out point) a track can carry two
section markers, ordinary cues with their own roles in the shared `CueEditorSession`, so Cue Forge
and both Flow Builder decks get them:

| Marker | Role / type | Region | Export |
|---|---|---|---|
| Intro end | `CueRole.IntroEnd` / `CuePointType.IntroEnd` (6) | Intro cue (or 0) → Intro end | memory cue "Intro end" |
| Outro | `CueRole.OutroStart` / `CuePointType.OutroStart` (7) | Outro → end of track | memory cue "Outro" |

- **Set**: `SetIntroEndAtPlayheadCommand` / `SetOutroStartAtPlayheadCommand` (Sections button, Shift+I /
  Shift+O), `SetIntroEndAtCommand` / `SetOutroStartAtCommand` (waveform right-click). Snapped to the bar
  (or the coarser snap resolution) when Snap is on; one marker per section (setting again moves it,
  choosing the role in the inspector takes it from the other cue); the intro must end before the outro
  starts. Memory cues (no pad), user cues, one undo step. Dragged / nudged like any cue.
- **Regions**: `SectionMarkers.IntroRegion` / `OutroRegion`; tinted with `BrushSectionIntro*` /
  `BrushSectionOutro*` in `CueForgeWaveformControl`, `CueForgeOverviewControl` and (via
  `TimeRegionOverlay`) the deck waveforms. Session exposes `IntroRegionStart/End`, `OutroRegionStart/End`.
- **Suggestion**: hosts pass the phrase segments (`SetStructureHints`, read-only). `SectionMarkers.Suggest`:
  intro end = end of the leading Intro phrases, else the first drop; outro = start of the trailing Outro
  phrases, else the phrase boundary after the last drop's main section (the run of drop phrases), else
  last drop + 32 bars. `SectionSuggestionText` + `UseSectionSuggestionCommand` ("Use suggestion").
- **Persistence**: the CuePoints table (integer types, no schema change); Cue Forge's auto-generate always
  keeps them.
- **Planning**: `TransitionPlanService.BuildStructure` reads them into `TrackStructure.IntroEndMarker` /
  `OutroStartMarker`; `TransitionPlanner.ComputeSections` trusts them over its estimates, so the Auto
  plan mixes out in A's outro and in over B's intro (a marked early outro is honoured before half the
  track). `TransitionEngine.OptimizeTransition` prefers the Outro marker as mix-out.

## Click to prelisten

A single click on a cue flag (Cue Forge waveform + overview, Flow Builder deck waveforms) or cue chip
calls `CueEditorSession.PrelistenCue`: select it and play from exactly the cue through the host's
`ICueAudition` (Cue Forge borrows the shared player; a deck uses the library preview player; both seek
with `ExactSeek` for FLAC/M4A/AIFF). Clicking the playing cue again, or Space, calls `StopPrelisten`
(`ICueAudition.Stop`). The decision click vs drag is `MarkerGesture` (4 px); a click never edits.
Outside Edit cues mode a deck click also makes the cue the mix-out / mix-in point.

Playback starts exactly on the cue: `PlayFrom` seeks first, and the player waits for a pending
`ExactSeek` decode-forward (FLAC/M4A) to finish before opening the output. Starting the output
while that background seek was still running let the reader deliver samples from its old position,
heard as "playback starts before the cue".

**The playlist gets its track back.** Cue Forge only ever borrows the shared player: `PlayerBorrow`
remembers the playlist's file, title/artist, position and whether it was playing. Saving (Save /
Ctrl+S, and the auto-save on track switch) and leaving the page both hand the player back to that
track at its old position, and **resume it when it was playing** — prelistening pauses the mix, but
the mix continues once the edit is saved instead of staying silent on the inspected track. The
queue's `CurrentTrack` is never replaced by the borrowed file, so auto-advance and next/previous
keep working.

## The docked browser follows the playlist, not a snapshot

The left browser is a view of one playlist: `LoadPlaylistBrowserAsync` reads it with
`ILibraryService.GetPagedPlaylistTracksAsync(playlistId, downloadedOnly: true)`, whose default order is
the persisted `SortOrder` (then `TrackNumber`, then `Id`). That list also drives the highlighted row,
`BrowserPosition` ("Track 3 of 24") and `PreviousTrackCommand`/`NextTrackCommand`.

Because the view model is a singleton, the list used to be exactly what the playlist looked like when
the page was last open. Reordering the playlist elsewhere — Library's **Reorder for better flow** /
**Auto-Arrange**, **Automix**, or Flow Builder's **Save order** — left Cue Forge showing the old
sequence until the app restarted. Two things keep it current now:

- **`OnViewActivatedAsync`** re-reads the browser on every visit to the page (after following the
  playing track), so a reorder done while Cue Forge was closed is picked up.
- **`PlaylistTrackOrderChangedEvent`** is published by `LibraryService.SaveTrackOrderAsync` — the one
  write path for playlist order — and Cue Forge re-reads when it names the selected playlist (and the
  Library grid refreshes for it too). A load that finishes after a newer one started is discarded
  (`_browserLoadVersion`), so a slow response can't restore an older order.

`SaveTrackOrderAsync` also guarantees the order readers rely on: after any reorder the playlist's rows
carry `SortOrder` 1..N — one row per position, no ties — including rows the arrange operation didn't
process (a partial list is treated as a permutation among the positions those rows already occupy).
Before that, "Reorder for better flow" only wrote the rows that happened to be loaded in the
virtualized grid, leaving duplicate positions behind; `ORDER BY SortOrder` then had no defined answer,
so the grid, Cue Forge and the player could each show a different order.

## Transition overlay (Flow Builder)

`TransitionOverlayModel` (pure) puts A's outgoing part and B's incoming part on one timeline in seconds
at the project tempo (A's BPM): 0 = mix-out = where B comes in; B runs at `ProjectBpm / IncomingBpm`.
Range = lead-in (A alone) + blend window (Length) + lead-in (B alone), the same layout as Preview, so the
preview position maps onto it (`OverlayPlayheadSeconds`). `MixTransitionViewModel.RefreshOverlay` rebuilds
it on every mix point, nudge, Length, preset or tempo change. `TransitionOverlayControl` draws both
envelopes (token colours), the shaded blend, both gain curves (same automation as playback), EQ /
bass-swap markers and bar numbers (1 = first blend bar); geometry is cached, frames don't allocate.
Dragging B shifts the mix-in (snapped to B's bars, Shift = beats) through `SetMixInFromOverlayCommand`;
mix-point changes are undoable (`UndoMixPointCommand`, Ctrl+Z).

## State Management

### Working Draft Isolation

All edits operate on `CueEditorSession.Cues` (in-memory `ObservableCollection<OrbitCue>`; `OrbitCue`
raises change notifications and the session bumps `CueRevision` on every change). Nothing writes to
SQLite until Save.

- **Revert** → re-fetches the stored rows; undoable (Cue Forge confirms first)
- **IsDirty / IsSaved** — set explicitly by every edit, cleared by load, save and revert; drive the
  "Unsaved changes" / "Saved" indicator. `StatusText` + `IsStatusError` carry the last result.
- Moving to another track (Cue Forge) or pair (Flow Builder) saves a dirty set first; if that save
  fails, Cue Forge stays on the track.

### Undo / Redo

- Max 50 snapshots (`CueEditorSession.MaxUndoHistory`)
- Each mutating operation pushes a snapshot before changing `Cues`
- Snapshot = `OrbitCue[]` deep copy (all fields)
- Redo stack is cleared on any new edit
- Waveform drags: Cue Forge's control sends `CueDragStartedCommand` (snapshot) before moving; the
  transition waveform doesn't, so the session keeps each cue's pre-edit time/source and builds
  the undo step from that on `CueUpdatedCommand`. A click that didn't move a cue is not an edit.

### Two editors on one track

Cue Forge and a Flow Builder deck can have the same track open. Each session keeps its own
working copy; `CueSessionRegistry` links them:

1. When a session saves, every other session on that track is told.
2. A peer with no unsaved edits reloads from the store immediately (so a Flow Builder edit shows
   up in Cue Forge, and the reverse, as soon as it's saved).
3. A peer with unsaved edits keeps them and shows a warning (`HasExternalChanges`): Save keeps its
   version (replacing the other), Revert loads the other.
4. Opening a track another editor has unsaved edits for shows a warning saying so.
5. Flow Builder saves its decks before "Open in Cue Forge"; deck cue generation also notifies peers.

Sessions are held weakly, so a host that is never disposed doesn't leak.

### Session Persistence

`AppConfig.CueForgeLastTrackHash/Title/Artist` — written to config JSON on every `LoadTrackAsync`. On next launch, `CueForgeViewModel` constructor restores the last track immediately.

## Key Identifiers

| Concept | Identifier |
|---------|------------|
| Track identity | `TrackUniqueHash` (SHA256 of file content) |
| Cue slot mapping | `CuePointEntity.SlotIndex` 0–7 = Hot Cue pads, -1 = Memory Cue |
| Cue types | `CuePointType`: `Intro=0, Outro=1, Drop=2, Breakdown=3, Build=4, PhraseBoundary=5, IntroEnd=6, OutroStart=7` (stored as integers) |
| Cue roles (in-memory) | `CueRole`: `Intro, KickIn, Breakdown, Breakdown2, Drop, Climax, Vocals, Outro, Bridge, Build, PhraseStart, Custom, IntroEnd, OutroStart`; role ↔ type via `OrbitCue.RoleFromType` / `TypeFromRole` (every editor, incl. the workstation) |
| Loop flag | `IsLoop=true` + `LoopEndSeconds` on the same entity |
| User vs auto cue | `CueSource.User` — never overwritten by Auto-Generate; `CueSource.Auto` — replaced on re-generate |

## Extension Points

To further develop Cue Forge, the highest-leverage areas are:

- **`CueForgeWaveformControl`** — all visual features (zoom, scroll, waveform zoom-in, waveform color schemes) live here. Rendering is pure GDI-via-Avalonia `DrawingContext`, no external libs.
- **`Engine/Cueing/CueGenerationService.cs`** — add a Path 4 or improve Path 2/3. All paths receive the same `AnalysisPipelineResult` so new signals just need to be added there.
- **`BuildAnalysisResultFromFeatures`** in `CueForgeViewModel` — the bridge between stored `AudioFeaturesEntity` columns and `AnalysisPipelineResult`. When new analysis columns are added to `AudioFeaturesEntity`, wire them here for the Auto-Generate fast path.
- **`CuePointEntity` + migration** — to store new cue metadata (e.g., confidence, phrase label, color scheme) add columns here and create a new EF migration.
- **`RekordboxXmlExporter`** — to change how cues export to DJ software (e.g. Pioneer CDJ, Engine DJ, Serato), start here.
